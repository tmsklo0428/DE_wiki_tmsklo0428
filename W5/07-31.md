- **DE 프로젝트 주제 피드백:**
  - 문제 해결을 위해 핵심 **지표(인덱스)** 를 선정해야 한다. 인덱스는 우리가 개선하고자 하는 값이며, "기존 인덱스가 우리 걸 쓰면 이렇게 변한다"는 before/after가 나와야 한다.
  - 풀어야 할 것은 "회사의 반복 업무"다.
  - 교통정책의 목표는 싸게, 빠르게, 기다리지 않고 가는 것이다. 택시가 잘 먹고 잘 사는 것이 목표가 되면 안 된다.
  - 한 문제를 풀어 다른 문제가 계속 생기더라도, 그중 지표가 개선되는 하나의 문제를 잡고 문제와 대상을 구체적으로 정의할 것.
  - 다른 팀 예시: 인덱스 = 자전거 평균 수명
- **우리 팀 주제 3차안 (방향 전환)**
  - 누가: 이벤트 쿠폰 운영 담당자(를 지원하는 데이터 엔지니어)
  - 어떤 문제: 쿠폰 효과를 판단하려면 실험군/대조군 데이터가 매 회차마다 준비되어야 하는데, 수동으로 만들면 회차마다 반복 작업이 들고 재현이 어렵다.
  - 해결 방법: 실험 데이터를 회차마다 자동으로 구성하는 파이프라인을 만든다.
  - Input: Raw Trip 데이터 + 회차 Config(기간, Zone 범위, treatment 비율, effect 가정) / Output: 회차별 실험군·대조군 집계 테이블 (zone별 평균·표준편차·건수, 회차 ID로 누적 저장)
  - 논의 과정: 승객의 이동 목적·관심사를 알아도 광고 노출은 의미가 없고, 이벤트가 있어도 택시를 타지 않을 손님에게는 이벤트도 의미가 없다. → 적절한 때와 사람을 선정하는 문제로 좁혔다.
  - 한계: 실제 회사에는 승객 ID, 쿠폰 지급 로그, 사용 여부가 모두 있어 Uber 내부에 이미 존재할 가능성이 높다.
  - 피드백: 쿠폰 평가 모델이 필요하다. "무엇을 판단할까"가 아니라 "어떤 데이터 흐름/인프라가 필요한가"에서 시작할 것.
